# ESP32-32E guide

The `esp32-32e` target is for the LCDWiki-style 3.2 inch board: a classic
ESP32-32E with 4 MB flash, no PSRAM, an ILI9341-compatible 320×240 SPI panel,
and XPT2046 resistive touch. Select it explicitly; `buddy` remains the default
for the ESP32-S3 prism.

Hold the board in portrait with USB-C at the top. The default canvas is
240×320: Lump fills the top 240×240, and a 240×80 band below shows WORK, WAIT
and DONE counts, an offline plug, and a brief TAP ring for accepted presses.
Counts include zero; values above 999 show `999+`. After the host times out,
the last counts stay visible with OFF beside them. Reset clears the counts.

## Pins

| Function | GPIO |
|---|---|
| LCD / touch SCLK | 14 |
| LCD / touch MOSI | 13 |
| LCD / touch MISO | 12 |
| LCD CS | 15 |
| LCD DC | 2 |
| LCD reset | None (`-1` in the driver) |
| Backlight | 27, active high |
| XPT2046 CS | 33 |
| XPT2046 IRQ | 36 (observed, but does not gate polling) |

The LCD and touch controller share SPI2. Display writes use 20 MHz, reads
500 kHz, and touch reads 1 MHz. Board variants can have different wiring;
the profile is in `firmware/src/board_esp32_32e.h`. SD, speaker, battery
monitoring and the RGB LED are unused.

## Flash and art layout

| Region | Offset | Size |
|---|---|---|
| Bootloader | `0x1000` | Before the partition table |
| Partition table | `0x8000` | Before NVS |
| NVS | `0x9000` | `0x5000` (20,480 bytes) |
| PHY init | `0xe000` | `0x1000` (4,096 bytes) |
| Program | `0x10000` | `0x170000` (1,507,328 bytes) |
| Art | `0x180000` | `0x270000` (2,555,904 bytes) |
| Coredump | `0x3f0000` | `0x10000` (65,536 bytes) |

Art is **120×120 at 8 fps**, doubled in both axes to 240×240 during playback.
The smaller v4 file records its dimensions and length so the firmware can map
only the bytes it needs in the classic ESP32's limited address space. All
moods, transitions and gags remain, including body-colour tinting. The supplied
file is 2,166,922 bytes, with 764 unique frames, 10 moods and 177 sequences.

Like the S3's `firmware/data/lump.bin`, the converted art is committed so a
first flash does not need a browser or a new drawing export. From the repository
root, this command reproduces `firmware/data/lump-esp32-32e.bin` byte for byte:

```bash
python3 tools/shrink_art.py --source firmware/data/lump.bin --output firmware/data/lump-esp32-32e.bin --size 120 --fps 8
```

It uses only Python's standard library, samples pixels without interpolation,
deduplicates frames, and preserves the last pose of transitions and events.
Regenerate it after exporting new S3 art. The source file is kept intact.

## Build and flash

Install Python 3 with venv/pip support, then prepare the tools from the
repository root:

```bash
python3 -m venv tools/.pio-venv
tools/.pio-venv/bin/pip install platformio
python3 -m venv tools/.venv
tools/.venv/bin/pip install esptool pyserial
```

On Linux, give your login and user services access to the `dialout` group as
described in the [Linux setup](../README.md#linux). The flasher uses `sg dialout`
for USB access. Set `PORT` to your board's serial device; a stable
`/dev/serial/by-id/...` path works too. The examples use `/dev/ttyUSB0`.

On macOS, the bridge, Wi-Fi setup and flasher discover `/dev/cu.usbmodem*`,
`/dev/cu.usbserial-*` and `/dev/cu.wchusbserial*`, in that order. Existing S3
modem ports keep priority. The bridge and Wi-Fi setup verify each candidate
with the `?` state query before using it. Set `PORT` explicitly when flashing
if more than one board is connected; the macOS examples below use
`/dev/cu.usbserial-0001`, which you must replace with your board's path.

Before flashing, save a full **4,194,304-byte** recovery image. Close serial
monitors and stop the bridge if it is running (`systemctl --user stop
deskbuddy-bridge.service` on Linux, or `launchctl bootout
"gui/$(id -u)/com.deskbuddy.bridge"` on macOS), then read the flash.

Linux backup:

```bash
mkdir -p backups
sg dialout -c 'tools/.venv/bin/python -I -m esptool --chip esp32 --port /dev/ttyUSB0 --baud 921600 read-flash 0 0x400000 backups/esp32-32e.bin'
```

macOS backup:

```bash
mkdir -p backups
tools/.venv/bin/python -I -m esptool --chip esp32 --port /dev/cu.usbserial-0001 --baud 921600 read-flash 0 0x400000 backups/esp32-32e.bin
```

Restart the bridge afterward if you stopped it: `systemctl --user start
deskbuddy-bridge.service` on Linux, or `launchctl bootstrap "gui/$(id -u)"
"$HOME/Library/LaunchAgents/com.deskbuddy.bridge.plist"` on macOS. Keep the
backup somewhere safe; the `backups/` directory is ignored by Git.

Linux flash:

```bash
BACKUP="$PWD/backups/esp32-32e.bin" PORT=/dev/ttyUSB0 tools/flash.sh esp32-32e
```

macOS flash:

```bash
BACKUP="$PWD/backups/esp32-32e.bin" PORT=/dev/cu.usbserial-0001 tools/flash.sh esp32-32e
```

The script requires `BACKUP` on every ESP32-32E flash, including `ART=0` updates.
It checks that the file is readable and exactly 4 MB, then prints its SHA-256
for your records. It uses `wc` and either `sha256sum` or `shasum -a 256`; no
fixed digest is required. With no `BACKUP`, it stops before building or pausing
the bridge and prints the exact read command for the selected port.
`NO_BACKUP=1` explicitly skips the check.

The flasher builds with one job, regenerates art, then writes the bootloader,
partition table, program and art at the offsets above. It pauses a running
bridge and resumes it on exit, including on an upload failure or HUP/INT/TERM.
An already stopped bridge stays stopped. If systemd state cannot be read
unambiguously, it stops before using the board.

For a build without flashing:

```bash
tools/.pio-venv/bin/pio run -d firmware -e esp32-32e -j 1
```

`ART=0` keeps the installed art, `SKIP_BUILD=1` reuses a build, and `PACED=1`
selects the paced uploader instead of plain esptool. Set `HEAVY_LOCK` to share
the build/upload lock with another job.

## Touch and panel tuning

Send newline-terminated commands over serial at **115200 baud**. Close the
bridge before opening another serial tool. Pressing anywhere plays a gag;
coordinates do not need calibration for this action. A held press triggers
once and must be released before another tap. The band shows a TAP ring for
450 ms when a press is accepted.

```text
i
T 600
P
P 1 0 0
```

`i` reports pressure, the peak since the previous query, raw XY, IRQ, physical
tap count and the threshold. `T <pressure>` accepts **1..4095**, with **600**
as the default. Higher values need firmer pressure. Raw XY are diagnostic
values rather than calibrated screen coordinates.

`P <invert> <bgr> <rotation>` tunes the display live: invert and BGR accept
**0 or 1**, and rotation accepts **0..7**. `P` alone reports the current
settings. Defaults are **`P 1 0 0`**: inversion on, RGB order (BGR off), and
portrait with USB-C at the top. The driver uses native 320×240 memory,
rotation offset 5 and MADCTL `0x20` for that portrait canvas. A change clears
and redraws the whole panel. Both panel tuning and touch sensitivity last
until reset; lowercase `p` remains the meeting-prep command.

## Optional hardware check and limits

With the bridge stopped, an owner can run the boot, protocol and animation
soak check on any explicit USB serial path:

```bash
sg dialout -c 'tools/.venv/bin/python tools/check_esp32_32e.py --port /dev/ttyUSB0 --seconds 120'
```

The checker resets the board, checks panel-memory readback and USB discovery
within three seconds, exercises moods, counters, touch diagnostics and panel
tuning, then resets to the normal offline/idle state. It accepts any Wi-Fi
state by default; `--wifi off`, `--wifi joining` or `--wifi connected` checks
an expected state without changing credentials. `--leave-counts W A U` leaves
a visible counter snapshot after the final reset. Check optical colours,
orientation, backlight and physical presses on the actual panel; memory
readback and a synthetic tap cannot establish those.

There is one program slot and **no OTA**: firmware and art updates are
**USB-only**. Wi-Fi commands on TCP 4210, pairing, mDNS and the clock remain
available. Wi-Fi startup is deferred until **5 seconds of firmware uptime**
so USB discovery can finish first; association and time sync remain
asynchronous. Variants with different panels or wiring may need a different
profile. The S3 target keeps its full-size art, IMU and OTA layout.
